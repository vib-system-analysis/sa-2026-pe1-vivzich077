# Тесты по требованиям и багрепортам

Учебный проект по теме «Системы искусственного интеллекта» (ПР04).

![CI](https://github.com/vib-system-analysis/sa-2026-pe1-vivzich077/actions/workflows/ci.yml/badge.svg)

Система анализирует требование или багрепорт и предлагает тест: что именно
проверить, с какими входными данными и какой результат считать правильным.
Баги, найденные в production, превращаются в регрессионные тесты, чтобы
предотвратить повторное появление ошибок. Подготовленный тест попадает в pull
request, а решение о его принятии остаётся за человеком.

## Зачем нужен проект

Связать требования с проверками и закрывать каждый найденный в production баг
тестом, а не обещанием.

## Что исследуем

- Как отличить проверяемую часть требования от описания намерения.
- Какие данные нужны для теста и откуда их получить.
- Как оценить, действительно ли тест полезен, а не просто проходит.
- Кто отвечает за тест, который начинает падать со временем.

## Процесс и результат

QA-инженер или разработчик регулярно пишет тесты по задачам и разбирает
production-баги. Система помогает перевести описание на естественном языке в
исполняемый код проверки. Результат работы — pull request в репозитории команды:
код проверяют и вливают люди, после чего тест остаётся частью проекта.

## Критерии успеха

- Предложенные тесты принимают без переписывания.
- Регрессионные тесты не дают уже исправленным production-багам возвращаться.

## Качество и безопасность

При проверке проекта учитываем следующие риски:

- Багрепорт может содержать недостоверные инструкции или данные.
- Нельзя проводить через тест изменения кода, которые никто не запрашивал.
- Качество теста нужно подтверждать его выполнением: он должен проверять
	ожидаемое поведение и выявлять ошибку, а не только завершаться успешно.

## Данные

Для исследования подойдут открытые репозитории с историей багов и тестов.
Дополнительный источник требований — собственный учебный проект команды.

## Запуск заглушки

Для локального запуска нужен Docker Compose:

```sh
cp .env.example .env
docker compose -f compose.dev.yml up --build
```

Сервис будет доступен на `http://localhost:8000`; health check —
`http://localhost:8000/health`. Это инфраструктурная заглушка: генерация тестов,
вызовы LLM и публичный production URL пока не реализованы.

Для запуска тестов и статических проверок без Docker:

```sh
python -m pip install -r requirements.txt
ruff check .
ruff format --check .
pytest
```

## Структура репозитория

- `app/` — HTTP-заглушка сервиса.
- `docs/prd.md`, `docs/system-boundary.md`, `docs/stakeholders.md`, `docs/hypotheses.md`, `docs/insights.md`, `docs/glossary.md`, `docs/brief.md` — продуктовые артефакты; роли, цели и интервью требуют подтверждения командой.
- `docs/research.md`, `docs/model-candidates.md`, `docs/experiments/` — кабинетный ресёрч и протокол пробы; реальные вызовы модели не выполнялись.
- `docs/quality/` — метрики, DoD и план датасета. Текущие 10 seed-записей синтетические, не интервью-данные.
- `.github/workflows/ci.yml` — CI для PR и push в `main`.
- `CONTRIBUTING.md`, `.github/pull_request_template.md` — правила разработки и шаблон PR.
- `docs/deploy.md` — локальный запуск и статус публичного стенда.

## Статус лабораторной

Документы и локальный CI-скелет подготовлены, однако ЛР1 ещё не полностью закрыта:
нужно провести 3–5 проблемных интервью, согласовать глоссарий и целевые метрики,
выполнить и зафиксировать реальные модельные пробы, заменить первые 10
синтетических примеров данными с интервью и развернуть заглушку на публичном
хостинге. Ссылки на результаты и URL добавлять только после фактической проверки.
