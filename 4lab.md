# Лабораторная работа 4. Граф системы Test Writer

## Цель

Представить систему графом и найти её узкое место расчётом, а не на глаз.

## Формулировка задания

### Что сделать

Постройте граф: элементы системы — вершины, связи — рёбра. У каждой связи
скажите, что по ней идёт: данные, материалы, команды, деньги, люди.

Запишите граф матрицей смежности. Матрицу храните данными — CSV или таблицей
Excel / Google Таблиц, — а не рисунком.

Посчитайте расчётом, который пересчитывается сам: скриптом или формулами в той
же таблице. Степени вершин, а дальше то, что имеет смысл для вашей системы, —
связность, кратчайшие пути, компоненты после удаления вершины.

Найдите точку отказа: вершину, при выпадении которой система перестаёт делать
то, ради чего существует. Проверьте догадку расчётом — уберите вершину из
матрицы и посмотрите, что развалилось.

Объясните результат словами: что именно перестанет работать, через какое
время это заметят, что продержится дольше.

### Что сдать

- Матрицу смежности данными.
- Расчёт, который пересчитывается: скрипт, который запускается и выдаёт числа,
  или таблица с формулами.
- Граф — рисунком или сгенерированный из тех же данных.
- Вывод о точке отказа с обоснованием.

### Почему здесь обязателен расчёт, а не числа руками

Это единственная работа курса, где артефакт обязан быть воспроизводимым.
Причина практическая: в системе появится ещё один элемент — и пересчёт должен
стоить нажатия клавиши. Матрица, посчитанная в тетради, устаревает в тот же
день, а на приёмке её нельзя пересчитать вместе с вами.

Два пути, оба годятся:

**Таблица с формулами.** Матрица на одном листе, степень вершины —
`=СУММ(B2:K2)` по её строке, выпадение вершины — копия листа без неё. Числа в
ячейках расчёта должны быть формулами, а не вписанными значениями: проверка
это видит.

**Скрипт на Python.** `networkx` закрывает всё, что здесь нужно, и посчитает
то, что в таблице неудобно: кратчайшие пути, связность после удаления
вершины.

## Границы модели

Смоделирован **целевой сквозной процесс Test Writer**: разработчик передаёт
задачу, система получает контекст репозитория, генерирует и проверяет тест,
запускает его изолированно и передаёт PR рецензенту. Это архитектурная модель
проектного процесса, а не утверждение о работающих интеграциях. В доступной
реализации API пока является заглушкой; журналы эксплуатации и измерения
времени отказа отсутствуют.

Вершины — участники и компоненты, направленные рёбра — передача данных или
команд. Направление показывает, кто инициирует передачу. Рёбра типа `data`
передают задачу, исходный контекст, тест или результат; `commands` — команды
получения контекста, запуска runner, создания PR или принятия решения. В этой
модели нет потоков материалов, денег или персонала между подразделениями.

## Артефакты и воспроизводимость

- [Матрица смежности](lab4/adjacency.csv) — направленная бинарная матрица `0/1`;
  строка — источник, столбец — получатель.
- [Матрица после удаления оркестратора](lab4/adjacency_without_orchestrator.csv)
  создаётся скриптом удалением его строки и столбца.
- [Типизированные рёбра](lab4/edges.csv) — вид и назначение каждого ребра.
- [Скрипт расчёта](lab4/analyze.py) на Python использует NetworkX. Он проверяет
  согласованность CSV, считает степени вершин, связность, кратчайший путь,
  центральность и изменение числа компонент при удалении каждой вершины.
- [Результаты расчёта](lab4/results.txt) и [граф](lab4/graph.svg) создаются тем же
  скриптом на основе CSV.

Запуск из каталога `lab4`:

```bash
python -m pip install -r requirements.txt
python analyze.py
```

## Результаты расчёта

Согласно `results.txt`, граф содержит 10 вершин и 17 направленных связей.
До отказа граф имеет одну слабую компоненту и одну сильную компоненту.
Кратчайший путь от разработчика к рецензенту — 4 ребра:
разработчик → HTTP API → оркестратор → Git-хостинг → рецензент. Оркестратор
имеет наибольшие входящую и исходящую степени — по 5 (суммарная степень 10).
Его нормированная betweenness centrality — 0.8542; это максимальное значение
среди вершин.

Удаление оркестратора разбивает оставшийся граф на 4 слабые компоненты — это
максимальная фрагментация среди проверенных одиночных отказов. Оркестратор —
основное структурное узкое место: через него сходятся API, адаптер репозитория,
модель, валидатор и runner, и через него инициируется передача PR на хостинг.
После удаления матрицы его строки и столбца компоненты состоят из
`{developer, api, git_host, reviewer}`, `{repo_adapter, repository, runner}`,
`{llm}` и `{validator}`. Без него запрос не проходит от входа к выполнению и
передаче результата.

Это не единственная функциональная зависимость: например, без runner тест не
будет выполнен, а без API не поступит новая задача. Скрипт проверяет удаление
строки и столбца каждой вершины и проверяет обязательные связи этапов процесса.
Поэтому удаление любой обязательной вершины делает сквозной процесс недоступным;
полная таблица есть в `results.txt`. Git-хостинг также является точкой
сочленения графа: без него рецензент отделяется от остальной системы, но
фрагментация меньше — 2 компоненты.

## Что перестанет работать и когда это заметят

При отказе оркестратора перестанет выполняться сквозная обработка новой задачи:
не будет скоординирован сбор контекста, генерация, проверка и запуск теста, а
новый PR не будет передан рецензенту. Пользователь заметит это при первой
следующей задаче. Точный интервал обнаружения в минутах определить нельзя:
нет развернутого процесса, мониторинга и данных об интервалах проверок.

Уже сохранённые исходники и существующие PR на Git-хостинге не исчезнут из-за
такого отказа; они смогут оставаться доступными дольше, чем остановленный
процесс генерации. Это качественная оценка последствий, а не измеренный SLA.

## Ограничения

Топология целевой системы выведена из проектного процесса Test Writer. Связи
не означают, что соответствующие сервисы уже подключены; весов, вероятностей
отказа, резервирования и временных метрик нет. Поэтому расчёт показывает
структурную центральность и эффект удаления вершины в заданной модели, но не
вероятность аварии и не фактическое время восстановления.
